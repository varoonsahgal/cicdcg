Before you click anything

Three rules for a shared account

1 · Your number. You are signed in as participant-NN. Every name you create contains your two digits: cicd-lab1-participant-07, participant-07-webserver. Fifteen people are doing this at once; names must not collide.
2 · Your region. US West (Oregon) · us-west-2, top-right corner, every time. "I can't find the thing I just made" is a region problem nine times out of ten.
3 · Your stuff only. You will see other students' pipelines and servers. Looking is fine; clicking Edit is not. In Lab 3 editing a neighbour's deployment group breaks their lab and teaches you nothing about yours.
💡
The loop you will use all day

Change something → upload it → watch the pipeline → read what went red → fix one thing → go again. Resist changing two things at once. The pipeline will always tell you what is next; your job is to read it carefully.

Why

Why CI/CD? A short story about Friday

Friday, 16:40 · a team without a pipeline The release is "ready". Priya builds it on her laptop (Java 17, because she upgraded last month). Tom tested a different build on his (Java 11). Someone copies the jar to the server over SSH, restarts the service by hand, and watches the logs. It fails. Was it the jar, the Java version, the config file Tom edited directly on the server in March, or the step everyone forgot? Nobody knows, because nobody can reproduce what just happened. The weekend is gone.
Friday, 16:40 · the same team with a pipeline Priya pushes a change. A clean container that nobody has ever logged into downloads the code, installs exactly Java 17 because the recipe says so, compiles, runs 212 tests, and produces a versioned artifact. A second robot copies that exact artifact to the server, runs the start script, checks the page answers, and marks the deployment green. It took six minutes and Priya watched it from the kitchen. If it had gone red, the previous version would still be serving customers. She goes home.

The four things a pipeline buys you

🧊ConsistencySame steps, same tools, same versions, every time. "Works on my machine" stops being an argument because there is no "my machine".
⚡Speed with feedbackMinutes from change to verdict. Problems are found while the change is still small and fresh in someone's head.
🛟SafetyVersioned, immutable artifacts make rollback a forward deployment of yesterday's known-good build, not an archaeology project.
🔭VisibilityEvery run has a log, a trigger, a version and a timestamp. "Who deployed what, when, and did the tests pass?" is a click, not a meeting.
CIContinuous Integration: every change is built and tested automatically. Lab 1.
CDContinuous Delivery: every good build is deployable at the push of a button. Lab 2 + the approval challenge.
CDContinuous Deployment: …and the button is pressed by a machine. Lab 2's auto-trigger.

Vocabulary, once

Nine words you will hear all day

Source — the files humans wrote, stored somewhere the pipeline can fetch them (a Git repo, or in these labs a versioned zip in S3).
Build — turning source into something runnable: install tools, compile, test, package. Happens in a throw-away container.
Artifact — the output of a build. A jar, a zip, a container image. Versioned and never edited afterwards.
Pipeline — an ordered set of stages (Source → Build → Deploy), each containing actions. A new run is an execution.
Trigger — what starts an execution: a push, an upload, a schedule, a human clicking Release change.
Deploy — putting an artifact onto compute and starting it in the right order. CodeDeploy for servers; ECS/EKS for containers.
Environment — a complete copy of where the app runs: dev, test, prod. Good teams make them from code so they are identical.
Rollback — deploying the previous good artifact again. Only possible if you kept it.
Service role — the IAM identity a robot (CodeBuild, CodeDeploy, an EC2 agent, an ECS task) uses while working for you. Scoped to the job.

Concept · Lab 1

Anatomy of a build

A build has a recipe (buildspec.yml), an environment (a container image with tools in it), an input and an output. The recipe is a list of shell commands grouped into phases that always run in the same order.

🧯 Builds that bite

  • Tool versions "whatever is installed" (Java 11 vs 17 – Lab 1's planted bug)
  • Secrets pasted into the recipe
  • Output that nobody can trace to a source version
  • A green build that never ran the tests

✅ Builds that behave

  • Pinned runtime versions in the recipe
  • Secrets injected from Secrets Manager / Parameter Store at run time
  • Build number and commit stamped into the artifact
  • Tests as a gate: red test = red build = nothing ships
📝
Reading a red build

Open Phase details: the first red phase is the culprit. Open Build logs: the tool's own error is a few lines above CodeBuild's final "exit status" line. Then ask: is this my command, my environment, or a permission? Lab 3 turns that into a reflex.

Concept · Lab 2

Delivery versus deployment, and how CodeDeploy thinks

A pipeline is a sequence of stages. The difference between Continuous Delivery and Continuous Deployment is exactly one stage: a human approval before Deploy. Everything upstream is identical, which is why teams can move from one to the other without rebuilding anything.

CodeDeploy does not know what your app is. You tell it in appspec.yml: which files go where, and which scripts to run at which lifecycle hook. Hooks are the part people underestimate.

⚠️
The lesson students remember

In Lab 2 you misspell one service name, the deployment fails, and your site is down – not "still on the old version", down. Then you turn on automatic rollback, break it again, and the site stays up on the previous version while the pipeline is red. Both lights are telling the truth.

Read permission errors like a sentence

Every AWS AccessDenied has the same grammar: who (the principal ARN) is not authorized to perform what (the action) on which (the resource). Those three words are the diagnosis. Fix the missing verb; do not hand out *.

Concept · all labs

Security in CI/CD: the pipeline is production

A pipeline holds the keys to everything it deploys. Treat it with at least the care you give the servers. The habits below are built into the labs; tick them off as you meet them.

Concept · all labs

Consistency: why pipelines beat people

Humans are creative; deployments should be boring. Every planted bug in this course is a small inconsistency that a person would not notice and a pipeline refuses to tolerate:

  • A recipe that pins versions. runtime-versions: java: corretto17 means the build container is Java 17 on every run, forever, regardless of who triggered it. (Lab 1's bug is exactly this line being wrong.)
  • An artifact built once, deployed many times. The jar/zip/image that passed the tests is the thing that ships. Rebuilding "the same code" on the server is not the same thing.
  • Idempotent scripts. dnf install -y httpd and systemctl enable httpd can run ten times with the same result. Scripts that assume a clean machine fail on the second deployment.
  • Infrastructure from code. Lab 3's fifteen environments were created by one Terraform file and can be reset to the exact same broken state in a minute. Fifteen hand-built environments would be fifteen different environments.
  • Tags and names generated, not typed. The tag the deployment group searches for and the tag on the instance should come from the same variable. Lab 3's bug 3 is what happens when a human types one of them.
  • Verification in the pipeline, not in someone's head. "I checked the page after deploying" does not scale to 40 deploys a day. A ValidateService hook does; so does a Build stage that refuses a bundle naming a script that is not there (Lab 2, Part 9).

Concept · Lab 3

Why green is not the same as correct

Each stage of a pipeline verifies its own contract. CodeBuild asks "did every command exit 0?". CodeDeploy asks "did every hook exit 0 and every file copy succeed?". Nobody asks "is the website right?" unless you make them.

🟢 Green, and wrong

  • The build packaged appspec.yml and the scripts but forgot index.html. Build green. Deploy green. Website: Apache's test page. (Lab 3, bug 6)
  • A deployment "succeeded" because the start script exited 0 – and the process crashed one second later.
  • The tests passed because there were no tests.

🧪 Make the pipeline check the outcome

  • A ValidateService hook that fetches the page and greps for a sentence (Lab 2 Challenge C, Lab 3 Challenge A).
  • Container health checks and Kubernetes readiness probes: traffic only reaches containers that answer (Labs 4, 5).
  • A build step that fails if the artifact lacks a required file.
  • Synthetic monitors after deploy; alarms wired to automatic rollback.

Concept · Labs 4 and 5

Containers: ECR, ECS and EKS in one picture

Labs 1–3 deployed files onto a server you had to prepare (install Apache, install an agent). Containers flip that: the image carries its own operating system userland, runtime and app, built once in CI; the server only needs a container runtime. Where Lab 2 copied a page into Apache, Lab 4 ships the whole Apache.

Image — a read-only stack of layers produced by a Dockerfile. Identified by a name + tag (…/mission-control:v7) and, more precisely, a digest.
Container — a running instance of an image with its own filesystem view, network and process tree. Ephemeral by design: nothing you write inside survives a restart.
Registry (ECR) — where images live between build and run. Private per account; scans images for CVEs; the orchestrator pulls from it using a role.
Orchestrator (ECS / EKS) — keeps the desired number of containers running, replaces failed ones, rolls out new versions, and wires in load balancers.
Compute (Fargate / EC2 nodes) — where containers actually execute. Fargate: you never see a server. EC2 / managed node groups: you do, and you pay for the whole box.
Task definition / Pod spec — the versioned recipe for one unit of work: image, CPU, memory, ports, environment, health check, logging, roles.

📝
Same physics, different vocabulary

Both orchestrators do the same four things: schedule (find room), supervise (restart what dies), roll out (new version in, old version out, without downtime) and expose (give it an address). Lab 4 teaches those with ECS words; Lab 5 repeats them with Kubernetes words. If you can explain a rolling update in one, you understand it in the other.

Reference

Glossary

appspec.yml
CodeDeploy's instruction file: files to copy and hooks scripts to run at lifecycle events.
Artifact store
The S3 bucket CodePipeline uses to pass files between stages. Created by the wizard; shared by every pipeline in the account.
Blue/green deployment
Start the new version on new capacity, switch traffic, retire the old. Avoids the "stopped old, failed to start new" gap of in-place deployments.
buildspec.yml
CodeBuild's recipe: phases of shell commands, artifacts to keep, optional reports, env, cache.
Circuit breaker (ECS)
Stops a rolling deployment that keeps failing and, optionally, rolls back to the last steady state.
CodeDeploy agent
Software on each EC2 instance that polls CodeDeploy, downloads bundles and runs hooks. No agent, no deployment.
Deployment configuration
How many instances CodeDeploy changes at once: AllAtOnce, HalfAtATime, OneAtATime, or a custom minimum-healthy-hosts rule. The blast-radius dial (Lab 2, Part 10).
Deployment group
Which instances (by tag or Auto Scaling group) and how (all at once, one at a time, with rollback, with triggers).
EventBridge
AWS's event bus. The pipeline wizard creates a rule that starts your pipeline when a new object version is written; Lab 1's Mission G writes a rule that e-mails you when a build fails.
Fargate
Serverless compute for containers: you specify CPU/memory per task and never manage an instance.
Idempotent
Safe to run repeatedly with the same result. Deployment scripts must be.
Instance profile
The wrapper that lets an EC2 instance assume an IAM role. Created automatically when you make an EC2 role in the console.
Lifecycle hook
A named moment in a deployment (BeforeInstall, ApplicationStart, ValidateService…) where your script runs. Non-zero exit = failed deployment.
Namespace (Kubernetes)
A virtual partition of a cluster with its own names, RBAC and quotas. Your sandbox in Lab 5.
Polling vs events
Two ways a pipeline notices a change: ask every minute (Lab 3) or be told immediately (Lab 2's EventBridge rule).
Readiness / liveness probe
Kubernetes health checks: readiness gates traffic, liveness triggers a restart.
Rolling update
Replace old copies with new ones gradually, keeping capacity up. ECS services and Kubernetes Deployments both do this by default.
Secrets Manager / Parameter Store
Where secrets and configuration live. A build references them by name in env:; the service role fetches the value at run time; the log masks it.
Service role
An IAM role an AWS service assumes to act for you; its trust policy names the service (codebuild.amazonaws.com).
SNS
Simple Notification Service: a topic that fans one message out to e-mail, SMS, chat webhooks or Lambda. Every alert in these labs ends in an SNS topic.
Task definition
ECS's versioned recipe for a task: image, resources, ports, env, logging, roles. Immutable per revision.
Versioning (S3)
Keeps every version of an object. Required for S3 pipeline sources; what makes rollback possible.
